# RoboSchool / ByByte — методологія уроків і курсів

Джерело: внутрішні рекомендації RoboSchool. Застосовуй разом із stepped-форматом ([reference.md](reference.md)).

## Роль агента

| Аспект | Правило |
|--------|---------|
| Роль | Методист STEM: програмування, робототехніка, електроніка, інженерне мислення для дітей |
| Мета програми | Учень **розуміє проблеми**, будує алгоритми, перевіряє рішення — не лише копіює код і терміни |
| Контекст | Практична STEM-платформа (RoboSchool / ByByte); уроки — у репо ByByteLessons |
| Вік (орієнтир) | 7–9, 9–12, 12–16 років; адаптуй за реальною готовністю, не лише за віком |
| Баланс | ~**80% практика / 20% теорія** (орієнтир); теорія — коли потрібна для наступного практичного кроку |

## Принципи навчання (2.1–2.15)

| ID | Принцип | Суть | У stepped-уроці |
|----|---------|------|-----------------|
| 2.1 | Проблема першою | Не починати з визначення терміна чи готового демо | `step:intro` — виклик/мета; крок 1 — задача, не лекція |
| 2.2 | Дослідницький підхід | Спостереження → прогноз → гіпотеза → експеримент → висновок | Окремі кроки «передбач результат» / «перевір»; `hint` лише після спроби |
| 2.3 | Діяльнісне навчання | Ельконін—Давидов, **Рєпкін**: задача → спосіб → перевірка → перенесення | Цикл стоп-блоків: задача → timer → `hint` → `dont_understand` → `know_answer` |
| 2.4 | Реальний продукт | PBL: пристрій/програма з метою, обмеженнями, критеріями успіху | Кожен урок — **працюючий проміжний результат**; великий проєкт — дрібні функціональні частини |
| 2.5 | Помилки й debug | Очікувана vs фактична поведінка; одна зміна → retest | Крок «налагодження»; підказки — **діагностичні питання**, не миттєве виправлення за учня |
| 2.6 | Поступове ускладнення | Одна (мала група) нових понять на урок | Див. [Ланцюжок понять](#ланцюжок-понять-фізичне-програмування) |
| 2.7 | Scaffolding | Підтримку зменшують з часом | Ранні уроки курсу: більше `hint`; пізніші: менше, більше самостійності + перенесення |
| 2.8 | Когнітивне навантаження | Малі порції; один крок — одна дія/поняття | **Один `step:N` = одна дія або одне поняття**; без зайвого тексту в кроці |
| 2.9 | Приклад перед самостійністю | Розібраний приклад → схожа задача → нова умова | `dont_understand` = розібраний приклад; наступний крок — менше підказок |
| 2.10 | Повторення | Розподілене в часі, не одна вага однакових вправ | У intro наступних уроків — коротка актуалізація; окремі кроки «знайди помилку» |
| 2.11 | Перенесення | Зміна **однієї** умови після опанування бази | Фінальний крок уроку — варіант задачі (поріг, датчик, порядок дій) |
| 2.12 | Формувальне оцінювання | Зворотний зв'язок конкретний, «що перевірити далі» | Текст `know_answer` / підказок — критерії перевірки, не «неправильно» |
| 2.13 | Вибір учня | Обмежений вибір (індикатор, параметр, додаткова функція) | У задачі — 2–3 осмислені варіанти, не безмежна творчість для початківців |
| 2.14 | Співпраця | Парна/групова лише якщо узгоджено; ролі чергуються | Фіксуй у методичних нотатках курсу; у markdown — опційний блок «ролі в парі» |
| 2.15 | Зв'язок із реалом | Навіщо поняття в реальних системах | 1–2 речення в intro або `hint`, не декоративні вставки |

| Етап | Тема |
|------|------|
| 1 | Керування виходом |
| 2 | Зчитування датчика |
| 3 | Змінні |
| 4 | Умови |
| 5 | Повторення |
| 6 | Функції |

| 9 | Автоматизація |

## Scaffolding → actions

| Етап підтримки | Що робить учень | Як відобразити в кроці |
|----------------|-----------------|-------------------------|
| 1 | Дивиться розібраний приклад | `dont_understand` з поясненням «чому так» |
| 2 | Повторює з `hint` | `hint` immediate + `timer` |
| 3 | Дороблює частину сам | Задача з неповним кодом / пропусками |
| 4 | Аналогічна задача, менше підказок | Менше actions або коротший `hint` |
| 5 | Нова ситуація | Останній крок — перенесення (2.11) |

## Налагодження (2.5) — зміст кроку

| Крок учня | Що включити в текст кроку / підказку |
|-----------|----------------------------------------|
| 1 | Яка **очікувана** поведінка? |
| 2 | Що **фактично** відбувається? |
| 3 | Одна гіпотеза про причину |
| 4 | Змінити **одну** умову або рядок |
| 5 | Повторний тест і висновок |

## Побудова курсу (backward design)

| Крок | Дія |
|------|-----|
| 3.1 | Визначити **кінцеві компетентності** і продукт курсу |
| 3.1↓ | Зворотний ланцюг: демонстрація → потрібні навички → перевірка → проміжні результати → список уроків |
| 3.2 | На кожен урок: **ціль ↔ діяльність учня ↔ перевірка** узгоджені (не лише копіювання коду) |
| 3.3 | Кожен урок — **видимий результат** (не «готуємось тиждень без робочого прототипу») |
| 3.4 | **Карта залежностей**: передумови → урок → що спирається далі |
| 3.5 | **Один фокус** на урок: одне поняття / тісна група; час на практику, debug, резерв |

## Алгоритм плану курсу (кроки 1–10)

| # | Задача |
|---|--------|
| 1 | Проаналізувати вихідні: вік, тривалість, обладнання, формат, продукт; уточнити, якщо бракує даних |
| 2 | Кінцеві компетентності |
| 3 | Кінцевий продукт: функції, обмеження, критерії готовності |
| 4 | Карта знань і залежностей |
| 5 | Проміжні навчальні результати (кожен — самостійна цінність) |
| 6 | Таблиця уроків (див. нижче) |
| 7 | Перевірка навантаження (нові поняття, час на debug) |
| 8 | Точки повторення і перенесення |
| 9 | Логіка: кожен урок спирається на попередній |
| 10 | Методичний аудит: перевантаження, прогалини, дублікати, нечіткі цілі |

## Таблиця загального плану курсу (колонки)

| # | Колонка |
|---|---------|
| 1 | Номер уроку |
| 2 | Назва |
| 3 | Головна проблема / виклик |
| 4 | Навчальна ціль |
| 5 | Нові поняття та навички |
| 6 | Передумови (що вже знає) |
| 7 | Практичний результат наприкінці уроку |
| 8 | Спосіб перевірки |
| 9 | Рівень самостійності |
| 10 | Зв’язок із наступним уроком |

Після таблиці: карта залежностей, компетентності, контрольні точки, повторення, ризики прогалин/перевантаження, пояснення логіки.

**Не** писати повні сценарії всіх уроків на першому етапі, якщо користувач не просив — спочатку узгодити архітектуру курсу.

## Етапи одного уроку → stepped

Гнучка модель; етапи можна об’єднувати в одному `step:N`, але порядок логіки зберігати.

| # | Етап | Де в уроці |
|---|------|------------|
| 1 | Актуалізація | Початок intro або перший крок короткого уроку |
| 2 | Проблема | Intro + заголовок кроку 1 |
| 3 | Прогноз | Текст задачі: «що станеться, якщо…» |
| 4 | Дослідження | Крок з експериментом / спостереженням |
| 5 | Пояснення | `dont_understand` або крок після невдалої спроби |
| 6 | Практика з підтримкою | `hint` + `timer` |
| 7 | Самостійна робота | Крок з мінімумом actions |
| 8 | Тестування | Критерії в задачі: різні умови / параметри |
| 9 | Налагодження | Окремий крок або секція в задачі (таблиця debug) |
| 10 | Рефлексія | «Чому працює» + `know_answer` |
| 11 | Перенесення | Фінальний крок: змінена умова |

## Диференціація (3 рівні)

| Рівень | Очікування | У контенті |
|--------|------------|------------|
| 1 — мінімум | Головна задача з підказками, **працюючий** результат | Базова задача + повний набір `hint` |
| 2 — очікуваний | Самостійно або з нормальною підтримкою + **пояснення** | Стандартний урок |
| 3 — виклик | Граничні випадки, вдосконалення, інша умова | Підзаголовок «Додатково» / останній крок перенесення |
| Бонус | Домашнє / творче продовження | Окремий крок або `published: false` extension |

Рівні відрізняються **глибиною мислення**, не кількістю однотипних вправ.

## Вікова адаптація

| Група | Фокус подання |
|-------|----------------|
| 7–9 | Послідовності, прості алгоритми, візуальне програмування, короткі цикли, спостереження результату |
| 9–12 | Змінні, умови, цикли; датчики/акuators; параметри; пошук помилок |
| 12–16 | Функції, декомпозиція, текстовий код, автоматизація з даних, системне тестування, компроміси |

## Наочність (§7)

| Елемент | Призначення |
|---------|-------------|
| Схема / фото / блок-схема | Зв’язок схема ↔ код ↔ поведінка пристрою |
| Таблиця | Порівняння, ролі компонентів |
| Код | Один фокус на блок; без зайвих рядків у кроці |
| Слайд/екран | Один крок = одна дія; мінімум тексту на екрані |

Не: декоративні картинки, зайві терміни, великі стіни тексту в одному `step`.

## Оцінювання (§8)

| Перевіряємо | Не достатньо сам по собі |
|-------------|---------------------------|
| Пояснює алгоритм | Працює пристрій без розуміння |
| Передбачає поведінку | Виконав копіювання крок-за-кроком |
| Змінює параметр і тестує | Швидкість / кількість рядків коду |
| Знаходить причину помилки | |
| Переносить принцип | |

Якщо урок — суто покрокова інструкція, додай коротку перевірку розуміння (`know_answer` + питання в тексті кроку).

## Критерії якості плану курсу (§12)

| Критерій |
|----------|
| Чіткі кінцеві компетентності |
| Логічна послідовність і залежності |
| Конкретний результат **кожного** уроку |
| Практика в центрі; не лише копіювання |
| Поступове зростання складності |
| Підтримка + самостійність + диференціація |
| Повторення і перенесення в нові задачі |
| Результати спостережні й перевірявані |
| Зростання самостійності до кінця курсу |
| Твердження про «ефективність методики» не виходять за межі доказів |

## Доказовість (§9)

| Правило |
|---------|
| Відокремлюй результати досліджень від методичних порад |
| Не вигадуй джерела, цифри, гарантії «100% результату» |
| Не стверджуй, що методика працює в усіх контекстах однаково |
